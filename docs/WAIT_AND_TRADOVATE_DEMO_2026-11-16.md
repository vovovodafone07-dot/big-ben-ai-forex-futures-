# نتيجة إصلاح WAIT وإعداد Tradovate Demo — 16 نوفمبر 2026

المنصة الحالية تستقبل إشارات TradingView وتفحص أدلتها؛ ليست مولداً مستقلاً لصفقات Forex/Futures، ولم يتحول هذا الإصدار إلى تنفيذ وساطة. ظهور WAIT لا يكفي لمعرفة هل السبب نقص البيانات أم غياب شروط الدخول؛ أُضيفت حالة صريحة لكل سبب، مع الحفاظ على منع الصفقات الوهمية والقديمة.

## الأخطاء التي أُصلحت

في `desk.py` و`scalping.py` كانت الصفوف الخام ذات الرمز `EURUSD` لا تتطابق مع طلب تحليل مطبع إلى `OANDA:EURUSD`. أصبحت أسماء الصفوف تُطبع قبل المقارنة، وتظل الرموز ذات prefix الصريح مستقلة؛ لا يُحوَّل مزود OANDA إلى FOREXCOM ولا تُخمن عقود شهرية من `NQ1!`. أُضيف اختبار webhook محلي إلى التحليل يثبت أن BUY صالحاً باسم مختصر لا ينتهي إلى WAIT بسبب المطابقة.

في `app.py:market_pulse_worker` كان استعلام `ORDER BY time ASC LIMIT 1000` يأخذ أقدم نافذة من مخزن أكبر من 1000 شمعة. أصبح يأخذ أحدث 1000 ثم يعيدها للترتيب الزمني. يثبت اختبار بقاعدة SQLite محلية من 1100 شمعة أن آخر شمعة حديثة تدخل التحليل. هذا لا يجعل Twelve Data بثاً حياً ولا يرفع وتيرة جلبه؛ ما زال التاريخ الثلاثي الرموز يتجدد في دورة محدودة كل ست ساعات.

كان `run_signal_analysis` يبتلع فشل التحليل أو امتلاء السعة دون إبلاغ حلقة retry، فتُسجّل المحاولة وكأنها انتهت. أصبح ينتظر سعة التحليل لمدة محدودة، ويعيد نتيجة نجاح/فشل واضحة، وتعمل إعادة المحاولة بحد ثلاث محاولات. بعد استنفادها يسجل الطابور فشلاً لا اكتمالاً. لا يعاد إرسال Telegram أثناء إعادة محاولة التحليل. لا يعني هذا طابوراً دائماً؛ يظل الطابور في الذاكرة وقد يتأثر بإعادة تشغيل الخادم.

أصبحت نتيجة desk تحتوي `data_state` و`signal_state` و`decision_reason_code` لتفريق `NO_DATA` و`STALE_DATA` و`NO_VALID_SIGNAL` و`VALID_SIGNAL`. يعرض قسم التحليل السبب بالعربية دون تغيير التخطيط أو شروط الاستراتيجية. لم تُغيَّر ملفات Pine أو Alerts.

## ما أثبته الإنتاج في هذه الجولة

في فحص مباشر عند 17:10:52 UTC ظهر Heartbeat فعلي للذهب `FOREXCOM:XAUUSD` بمصدر `2026-11-16T17:10:00Z`، واستقبال `17:10:06.655889Z`. آخر BUY/SELL ظلت SELL على `OANDA:USDJPY` بتاريخ `2026-11-13T21:35:00Z`، قديمة وليست فرصة جديدة. تحقق السجل المصادق عليه `/api/integrations` و`/api/analysis/runs` باستخدام جلسة المستخدم؛ لم يعد خطأ 401 مانعاً في هذه القراءة.

أظهر `/api/integrations` رمزاً حديثاً واحداً من 11 رمزاً وصل سابقاً. بيانات Forex الأخرى والفيوتشرز المرصودة كانت قديمة وقت الفحص. لذلك معالجة 66 رمزاً في الكتالوج لا تساوي وجود بيانات حديثة لكل رمز. لم يُرسل أي حدث اصطناعي إلى الإنتاج، ولم تُنشأ Alerts.

أحدث سجل مقروء للذهب عند `17:14:30 UTC` كان WAIT رغم حداثة الحدث: لم يرسل المصدر BUY/SELL صالحة، وكانت عدة checks للدخول في حالة FAILED. الوكلاء التسعة هنا أدوار فحص أدلة حتمية، وليست تسعة نماذج مستقلة تولد صفقات. مراجعة Gemini منفصلة؛ في فحص الصحة كانت `connection_verified=false` وآخر سبب `provider_timeout`. لم يُدّعَ نجاحها ولم تُختبر بطلب مدفوع جديد في هذه الجولة.

## Tradovate Demo

أُنشئ إعداد آمن باسم Tradovate Demo API للتحقق والقراءة فقط. الحقول هي `TRADOVATE_DEMO_USERNAME`, `TRADOVATE_DEMO_PASSWORD`, `TRADOVATE_DEMO_CID`, `TRADOVATE_DEMO_SECRET`. لم تكن القيم متاحة في البيئة عند آخر فحص؛ أعادت أداة التحقق `credentials_missing` دون إرسال أي طلب إلى الوسيط. لا يعني إنشاء البطاقة أن حساب الوسيط متصل، ولا ينقل إعداد Manus أسراره تلقائياً إلى Render.

الوحدة `platform/backend/tradovate_demo.py` لا تحتوي مسار كتابة أوامر. يقتصر اتصالها على `https://demo.tradovateapi.com/v1`: مصادقة POST موثقة، ثم قوائم GET الموثقة للحساب والمراكز والأوامر القائمة والتعبئات والأرصدة. تمنع Live وأي URL بديل والتحويلات HTTP، وتحد حجم الرد والمهلة، ولا تسجل أسراراً أو tokens أو رسائل خطأ خاماً. لا تعمل عند بدء الخادم، ولا توجد نقطة HTTP تقوم بالمصادقة تلقائياً. يظهر فقط وضع تهيئة Demo غير المتحقق في تقرير التكاملات المصادق عليه.

تشغّل المصادقة الحقيقية مرة واحدة بعد إكمال البطاقة:

```bash
python3 platform/backend/tradovate_demo.py --verify
```

تبقى `broker_execution=disabled` و`execution_kill_switch=true` وقائمة السماح `[]` كثوابت في هذه المرحلة، لا متغيرات قابلة لتشغيل التداول. النجاح لاحقاً يعني وصول المصادقة وaccount/list إلى Demo، لا موافقة تنفيذ ولا ترخيص بيانات. أي تنفيذ Demo يحتاج مرحلة مختلفة وقيوداً واختباراً وتأكيداً منفصلاً؛ لم يُبنَ Order Router في هذه الجولة.

تشير وثائق Tradovate الرسمية إلى اشتراك API Access وإنشاء API Key ومتطلبات أهلية للحساب، وتفصل Demo simulation عن خدمات بيانات السوق. تسجيل الدخول إلى واجهة Demo وحده لا يثبت أهلية API. ينبغي أن تأتي CID وSecret وكلمة مرور API من إعدادات API الفعلية، لا تخمينها أو وضع قيم دخول UI بديلة. لا يلزم ولا يُسمح في هذا العمل تفعيل تنفيذ Live.
